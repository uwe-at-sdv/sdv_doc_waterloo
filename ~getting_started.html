Getting Started¶

Let us assume you are about to build a Python module or write the documentation for an existing module. This section is meant to demonstrate how to get started with Waterloo Docstrings. We use Sphinx as primary text processing system in order to create human-readable documentation and Waterloo’s commandline tool waterlint for generating machine-readable documents from the original Python docstrings. If you are only interested in machine-readable documentation please skip sections Install Sphinx and Building a human-readable documentation.

Setup Root Directory¶

We assume the project’s root directory is denoted as ${ROOT} in the following sections. Navigate to this directory in your terminal before proceeding. We use the proxy names my_module for the module to be documented (or generally as a prefix for files related to this module), and my_module.py for the source file.

Virtual environment¶

We recommend to use a Python Virtual Environment for these initial tests. This protects your system installations of pip, sphinx and other modules which would upgraded otherwise, which is not necessarily what you want.

Create a Virtual Environment¶

There is quite a lot of documentation on venv, but since it is so easy to understand and to use, we recall the basic setup procedure here. You are currently in you project directory. Run the following command to create a virtual environment named wtrl_venv:

python3 -m venv wtrl_venv

This creates a directory wtrl_venv and adds a standard installation of Python.

Activate the Environment¶

Run the activation command corresponding to your operating system and shell.

Install Sphinx¶

By the time you read this section, you most likely have installed Sphinx, but if you are in a virtual environment as suggested in the previous section you need to install it there as well. First, please make sure you have the latest version of pip

pip install --upgrade pip

Now install Sphinx and any extension you need for your project.

pip install sphinx

You are still in the root directory. Now make a directory for the human-readable documentation.

mkdir doc
cd doc

Set up a sphinx-project, e.g. using sphinx-quickstart:

sphinx-quickstart

> Separate source and build directories (y/n) [n]: y
> Project name: My-Project
> Author name(s): My-Name
> Project release []: 0.0.1

Waterloo is not (yet) multilingual, so let’s use English as natural language.

> Project language [en]:

Try if it works

make clean && make html

Check with you browser (Replace ${ROOT} by your root directory): file://${ROOT}/doc/build/html/index.html

Waterloo Docstrings¶

Install Waterloo¶

In case you have not done this yet, please update your installation of pip.

pip install --upgrade pip

Proxy code is:

pip install .

Add extension in ${ROOT}/doc/source/conf.py

# -- General configuration ---------------------------------------------------
# https://www.sphinx-doc.org/en/master/usage/configuration.html#general-configuration

extensions = [
        # your other extensions here #
        "sdv.doc.waterloo.docitem_sphinx",
        ]

Set up path to your source files.

# -- Path setup --------------------------------------------------------------

# If extensions (or modules to document with waterloo docstrin) are in another
# directory, add these directories to sys.path here. If the directory is
# relative to the documentation root, use os.path.abspath to make it absolute.

# In case you don't have this already:
import sys

ROOT = "/path/to/my/project"
sys.path.insert(0, ROOT)

Adding a Waterloo Docstring to the code¶

Insert this simple docstring at the top of your module source file my_module.py. Indentation unit is the tab-character or four spaces. Here we have used four spaces so that you can simply paste it to your source code.

r"""
Preamble:
    profile:
        module
    normative_sections:
        Contract
Contract:
    general:
        |Must| serve as an example for a waterloo docstring.
"""

The next step is quite important, and you should apply it to each docstring you write. This validates the docstring formally. You can of course rely on the Waterloo Sphinx extension to detect formal errors, but the representation from the linter is more details and clearer.

waterlint validate --basedir . --obj my_module

Building a human-readable documentation¶

In order to see how Waterloo works, we add a simple directive to the Sphinx source, e.g. in index.rst which is okay for testing purposes:

.. wtrl_autodoc_module:: my_module

Generate doc and check with browser.

make clean && make html

In the browser you should see a compact, structured representation of the module docstring. Other object categories like classes and functions are added likewise, with directives.

Building a machine-readable documentation¶

As outlined in the introduction, LLMs get along with the original Waterloo docstrings, but it seems they prefer JSON, because it is not based on indentation, and validation is done through the established methods of using “JSON schema”. In order to create a machine-readable version of the docstring, make a directory for JSON docs. Since Waterloo Docstrings is a new project [2026] there is no established “best practice” for this, but we recommend to name it “doc-json”, so that AI-agents will easily find it.

mkdir doc-json

Now render your module documentation in JSON

waterlint render-json --basedir . --obj my_module --out-dir doc-json

And finally validate your JSON output.

waterlint validate-json --in doc-json/my_module.core.rfc-2119.json

No error message and exit code 0 means: JSON output is valid. If you are interested in the set of installed Waterloo JSON schemas, invoke:

waterlint list-schemas

Final remarks¶

These are the basic steps. For further reading please have a look at the examples in chapters chapers_examples and Docstrings - minimal and full examples. In case of doubt have alook the format specification in chapter Docstring format which contains the rules for building valid docstrings in normative form.
