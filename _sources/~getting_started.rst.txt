Getting Started
===============

Let us assume you are about to build a Python module or write the documentation
for an existing module. This section is meant to demonstrate how to get started
with Waterloo Docstrings. We use Sphinx as primary text processing system in order
to create human-readable documentation and Waterloo's commandline tool
:wtrl_cmd:`waterlint` for generating machine-readable documents from the original
Python docstrings. If you are only interested in machine-readable documentation
please skip sections :ref:`section_sphinx` and :ref:`section_building_human_readable_documentation`.


Setup Root Directory
--------------------

We assume the project's root directory is denoted as ``${ROOT}``
in the following sections. Navigate to this directory in your terminal
before proceeding. We use the proxy names :wtrl_mod:`my_module` for the
module to be documented (or generally as a prefix for files related to this module),
and :wtrl_file:`my_module.py` for the source file.

.. _section_venv:

Virtual environment
-------------------

We recommend to use a Python Virtual Environment for these initial tests.
This protects your system installations of :wtrl_lit:`pip`, :wtrl_lit:`sphinx`
and other modules which would upgraded otherwise, which is not necessarily what
you want.

Create a Virtual Environment
............................

There is quite a lot of documentation on :wtrl_lit:`venv`, but since it is
so easy to understand and to use, we recall the basic setup procedure here.
You are currently in you project directory. Run the following command
to create a virtual environment named ``wtrl_venv``:

.. code-block:: bash

	python3 -m venv wtrl_venv

This creates a directory :wtrl_file:`wtrl_venv` and 
adds a standard installation of Python.

Activate the Environment
........................

Run the activation command corresponding to your operating system and shell. 

.. list-table:: Activation Commands
	:widths: 20 30 50
	:header-rows: 1

	* - Platform
	  - Shell
	  - Command
	* - **Unix** / **macOS**
	  - Bash / Zsh
	  - :wtrl_lit:`source wtrl_venv/bin/activate`
	* - 
	  - Fish
	  - :wtrl_lit:`source wtrl_venv/bin/activate.fish`
	* -
	  - csh/tcsh
	  - :wtrl_lit:`source wtrl_venv/bin/activate.csh`
	* - **Windows**
	  - PowerShell
	  - :wtrl_lit:`./wtrl_venv/Scripts/Activate.ps1`
	* - 
	  - Command Prompt
	  - :wtrl_lit:`wtrl_venv/Scripts/activate.bat`
	* - 
	  - Git Bash
	  - :wtrl_lit:`source wtrl_venv/Scripts/activate`

.. note::
	**Windows/PowerShell:** If you encounter an execution policy error, you can allow script execution for the current session by running:
	``Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser``

Leave the environment with :wtrl_cmd:`deactivate` when you are done with this toturial.

.. _section_sphinx:

Install Sphinx
--------------

By the time you read this section, you most likely have
installed Sphinx, but if you are in a virtual environment as suggested
in the previous section you need to install it there as well.
First, please make sure you have the latest version of pip

.. code-block:: bash

	pip install --upgrade pip

Now install Sphinx and any extension you need for your project.

.. code-block:: bash

	pip install sphinx

You are still in the root directory. Now make a directory for the human-readable documentation.

.. code-block:: bash

	mkdir doc
	cd doc

Set up a sphinx-project, e.g. using :wtrl_cmd:`sphinx-quickstart`:

.. code-block:: bash

	sphinx-quickstart

	> Separate source and build directories (y/n) [n]: y
	> Project name: My-Project
	> Author name(s): My-Name
	> Project release []: 0.0.1

Waterloo is not (yet) multilingual, so let's use English as natural language.

.. code-block:: bash

	> Project language [en]:

Try if it works

.. code-block:: bash

	make clean && make html

Check with you browser (Replace :wtrl_var:`${ROOT}` by your root directory): :wtrl_file:`file://`:wtrl_var:`${ROOT}`:wtrl_file:`/doc/build/html/index.html`

.. _section_waterloo_docstrings:

Waterloo Docstrings
-------------------

Install Waterloo
................

In case you have not done this yet, please update your installation of :wtrl_lit:`pip`.

.. code-block:: bash

	pip install --upgrade pip

Proxy code is:

.. code-block:: bash

	pip install .

Add extension in :wtrl_file:`${ROOT}/doc/source/conf.py`

.. code-block:: python

	# -- General configuration ---------------------------------------------------
	# https://www.sphinx-doc.org/en/master/usage/configuration.html#general-configuration

	extensions = [
		# your other extensions here #
		"sdv.doc.waterloo.docitem_sphinx",
		]

Set up path to your source files.

.. code-block:: python

	# -- Path setup --------------------------------------------------------------

	# If extensions (or modules to document with waterloo docstrin) are in another
	# directory, add these directories to sys.path here. If the directory is
	# relative to the documentation root, use os.path.abspath to make it absolute.

	# In case you don't have this already:
	import sys

	ROOT = "/path/to/my/project"
	sys.path.insert(0, ROOT)

Adding a Waterloo Docstring to the code
.......................................

Insert this simple docstring at the top of your module source file :wtrl_file:`my_module.py`.
Indentation unit is the ``tab``-character or four spaces. Here we have used four spaces
so that you can simply paste it to your source code.

.. code-block:: python

    r"""
    Preamble:
        profile:
            module
        normative_sections:
            Contract
    Contract:
        general:
            |Must| serve as an example for a waterloo docstring.
    """

The next step is quite important, and you should apply it to each
docstring you write. This validates the docstring formally.
You can of course rely on the Waterloo Sphinx extension to
detect formal errors, but the representation from the linter
is more details and clearer.

.. code-block:: bash

	waterlint validate --basedir . --obj my_module

.. _section_building_human_readable_documentation:

Building a human-readable documentation
.......................................

In order to see how Waterloo works, we add a simple
directive to the Sphinx source, e.g. in :wtrl_file:`index.rst`
which is okay for testing purposes:

.. code-block:: rst

	.. wtrl_autodoc_module:: my_module

Generate doc and check with browser.

.. code-block:: bash

	make clean && make html

In the browser you should see a compact, structured representation
of the module docstring. Other object categories like classes and
functions are added likewise, with directives.

Building a machine-readable documentation
.........................................

As outlined in the introduction, LLMs get along with the original
Waterloo docstrings, but it seems they prefer JSON, because it is not
based on indentation, and validation is done through the established
methods of using "JSON schema".
In order to create a machine-readable version of the docstring, make a directory
for JSON docs. Since Waterloo Docstrings is a new project [2026] there is no established
"best practice" for this, but we recommend to name it "doc-json",
so that AI-agents will easily find it.

.. code-block:: bash

	mkdir doc-json

Now render your module documentation in JSON

.. code-block:: bash

	waterlint render-json --basedir . --obj my_module --out-dir doc-json

And finally validate your JSON output.

.. code-block:: bash

	waterlint validate-json --in doc-json/my_module.core.rfc-2119.json

No error message and exit code 0 means: JSON output is valid.
If you are interested in the set of installed Waterloo JSON schemas, invoke:

.. code-block:: bash

	waterlint list-schemas
